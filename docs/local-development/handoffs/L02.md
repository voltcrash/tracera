## Changed behavior

- **Containers.** Each worktree gets two PostgreSQL 18.6 + pgvector 0.8.6 clusters from `pgvector/pgvector:0.8.6-pg18-trixie`, pinned by digest (`scripts/database/container.mjs`).
  - `local`: named volume `tracera-<worktree-id>-local-data`; data persists across stop/start.
  - `test`: tmpfs, created with `--rm`, so stopping discards it.
  - Both publish only on `127.0.0.1`, with health checks (`pg_isready` over TCP inside the container).
  - Tooling uses `docker` on `PATH`, falling back to OrbStack's bundled CLI and `orbstack` context. Compose is not required.
- **Worktree ownership.**
  - Containers and volumes carry `dev.tracera.*` labels (profile, worktree ID, SHA-256 of the real worktree path).
  - Every command verifies labels and the exact port binding before use, stop, or deletion. Configuration copied from another worktree is refused.
  - A port held by another container or process is refused and the holder named. Commands accept no URLs or database names.
- **Ports.** L01 generated one port for both profiles. Roles are cluster-wide, so per-profile passwords need separate clusters; `scripts/environment/setup.mjs` now gives `test` the local port + 1.
  - Worktree identity moved to `scripts/environment/worktree.mjs`.
  - When the existing test profile has a stale port, setup fails with an instruction to delete only `.tracera/environment/test` (disposable generated credentials).
- **Roles.** Details are in `scripts/database/bootstrap.mjs` and `docs/environment.md`.
  - **Bootstrap** is the container superuser, reachable only via `docker exec`; its password is cleared. It creates the roles and installs `vector` into `template1`, since pgvector is not a trusted extension. Bootstrap SQL runs with `log_min_error_statement=panic` and terse errors, and output is redacted.
  - **Migrator** owns the database and all objects: `CREATEROLE`, but no superuser, `CREATEDB`, replication, or `BYPASSRLS`.
  - **Runtime** is created by migration 0024 as the migrator. Bootstrap sets its password after migration.
  - **Test provisioner** exists in the test cluster only. It has `CREATEDB`, `SET` on the migrator for migrator-owned run databases, and `pg_signal_backend`.
  - `PUBLIC` has no database privileges.
- **Compatibility finding.** Migration 0024's existing-role branch runs `ALTER ROLE tracera_runtime ... NOSUPERUSER`. Vanilla PostgreSQL 16+ permits that only for superusers; Neon's owner role allowed it.
  - The first local attempt failed with `permission denied to alter role`.
  - 0024 was not rewritten, and migrations do not run as superuser. Instead, each cluster hosts exactly one migrated Tracera database lifecycle: `db:local:reset` recreates the cluster, and `db:rehearse` starts a fresh test cluster.
- **Connection factory.** New `@repo/db/connection` (`packages/db/src/connection.ts`) selects the transport from the validated profile.
  - `local`/`test` use `pg` 8.23.0 (node-postgres TCP, pool max 10). `deployed` keeps Neon's pool with `poolQueryViaFetch`.
  - Unconfigured imports get a pool that rejects every query, never default `PG*` settings.
  - `configureDatabase` ends the replaced pool. `closeDatabase()` and `activeDatabaseTransport()` were added.
  - The Core storage integration test now builds its pool through the factory.
- **Migration 0029** (`0029_core_runtime_grants.sql`, generated with `drizzle-kit generate --custom` so the journal and snapshot stay consistent). 0027's 13 Core tables had no runtime grants, because 0024 revoked default privileges. The grants mirror each statement in `packages/db/src/core/repository.ts`:
  - `SELECT, INSERT, UPDATE`: runs, jobs, outbox, stage attempts, checkpoints;
  - `SELECT, INSERT`: snapshots, snapshot embeddings, report versions, report snapshots;
  - `INSERT` only: report claims, assessments, provenance edges, decisions.
  - Nothing grants `DELETE`. The snapshot has no schema drift from 0028.
- **Runtime grant audit.** `scripts/database/runtime-grants.mjs` lists expected runtime privileges for all 31 public tables. Legacy `alert_subscriptions` and `decay_events` have none. The analysis-control grants from 0024 were confirmed sufficient.
- **Environment.** The test profile's runtime and migration URLs may target `<TRACERA_DATABASE_NAME>_<run>` (`<run>` = 1–16 lowercase letters or digits). Tooling derives such URLs only through the new `withTestRunDatabase()`, which rewrites and reseals a sealed generated environment. The local profile still requires the exact name.
- **Launcher.** `--require-database` in `scripts/environment/run.mjs` now requires this worktree's labeled container to be running and healthy, replacing L01's TCP probe.
- **Commands.** Added `db:local:{start,migrate,status,stop,reset}`, `db:test:{start,status,stop}`, and `db:rehearse`. `db:migrate:local` (L01) was renamed `db:local:migrate`, because migration must be followed by a superuser runtime-password sync.
- **Rehearsal** (`scripts/database/rehearse.mjs`):
  1. Fresh test cluster, then a run database created as the provisioner.
  2. Full migration as the migrator. Journal/file/hash/timestamp verification.
  3. Second migration, requiring identical migration rows and schema/ACL fingerprint.
  4. Runtime privilege audit (tables, columns, schemas, databases, role attributes, memberships).
  5. `packages/db/test/postgres.integration.test.ts` with only the sealed runtime environment. The command fails on any failed or skipped test, or zero passed tests.
  6. Drop as the provisioner, verified, including after failures.
- **Docs.** `docs/environment.md` gains a "Local PostgreSQL" section. `README.md`, `apps/web/README.md`, `config/environment/local.generated.env.example`, and the plan status were updated.

## Configuration and migration instructions

- Existing L01 worktrees: if `vp run env:setup` reports a test-port mismatch, delete `.tracera/environment/test` and rerun it. Never delete `.tracera/environment/local` to fix this.
- Local workflow: `vp run env:setup`, `vp run db:local:start`, `vp run db:local:migrate`, then `vp run dev`. Use `vp run db:local:stop` to pause, and `vp run db:local:reset` to discard this worktree's development data.
- Rehearsal: `vp run db:rehearse`. It leaves the test cluster running; `vp run db:test:stop` discards it.
- **Deployment note (operator action when this reaches production):**
  - Migration `0029_core_runtime_grants.sql` must be applied from the deployed migration environment. It only adds grants.
  - With `pg` installed, `drizzle-kit` selects the `pg` driver over `@neondatabase/serverless`, so operator migrations use standard PostgreSQL TCP to Neon. The migration URL must include `sslmode=require`, as standard Neon URLs do.
  - The deployed web runtime still uses Neon's serverless transport. L02 made no deployment changes and ran no remote migrations.
- The container's initial `POSTGRES_PASSWORD` is a random value that is never stored, and bootstrap clears it. It remains visible, but unusable, in `docker inspect`.

## Limitations

- Each cluster supports one migrated Tracera database at a time because of 0024. Concurrent integration runs in the same worktree must be serialized; L03's runner should lock or recreate the test cluster per run.
- The provisioner's `SET` on the migrator lets it act as the migrator inside the disposable test cluster. This is required for `CREATE DATABASE … OWNER` and `DROP DATABASE` on PostgreSQL 16+. It does not exist in the local cluster.
- `packages/db/test/core-storage.integration.test.ts` still cleans up with `DELETE` through the runtime pool. Under the reviewed grants that cleanup fails with 42501; L03 must move cleanup to a privileged connection or drop the run database.
- Worktree ports still come from a hash and can collide. Collisions are detected and refused, not reassigned.
- Only Docker-compatible engines were verified (OrbStack). Podman and CI were not exercised; CI is L06.
- Credential-free local sign-in (L04) and offline analysis (L05) are not implemented. The health smoke test did not exercise auth or analysis routes.
- Human-gold annotation, paid evaluation, calibration, and release approval remain separate, unsatisfied Core gates. L02 does not clear the Core Task 03 storage-validation blocker.
