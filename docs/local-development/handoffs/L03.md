## Real PostgreSQL evidence

Repository operations ran as `tracera_runtime` against migrated PostgreSQL, while
bootstrap, migration, and cleanup used their separate roles:

- duplicate enqueue returned one created job and one idempotent replay, with one scoped
  outbox record;
- simultaneous workers acquired distinct jobs; a retried job incremented its attempt,
  received a new fencing token, and rejected the stale checkpoint;
- a different owner could not request cancellation; stale acknowledgement failed, and
  the valid worker moved the job and run to `canceled`;
- finalization intentionally failed after starting its transaction because referenced
  snapshots were absent; the report insert rolled back and the lease remained active;
- two concurrent finalizers produced exactly one success, one `StaleWorkerError`, and
  one report version;
- stored factual score, score null reasons, diagnostic labels, and published labels
  exactly matched the frozen report fixture;
- a different tenant could not read the first tenant's outbox, snapshot, checkpoint, or
  report.

The data and report were deterministic synthetic fixtures executed against a real
database. They are storage-correctness evidence, not real-world accuracy evidence.

## Configuration and migration instructions

Run `vp run env:setup` once in a worktree, then run either
`vp run test:core-storage` or `vp run @repo/db#test:core-storage`. Do not export database
URLs or pass a target. The command provisions, migrates, tests, and cleans up by itself.
Concurrent Core storage runs in one worktree are refused by an exclusive lock; separate
worktrees use distinct generated resources.

L03 adds no migration. The runner applies the existing immutable history through 0029
to a new database on every invocation. No production migration ran.
