## Changed behavior

- Generated local runtime configuration now includes a sealed, worktree-specific
  `TRACERA_APP_ORIGIN`/`TRACERA_APP_PORT` and exact `DEV_AUTH_BYPASS=true`. Rerunning
  setup adds missing L04 settings without rotating or exposing existing generated
  secrets. `vp run dev` binds the generated web port instead of shared port 3000.
- Local/test runtime validation rejects non-loopback, non-HTTP, or port-mismatched app
  origins before auth or database access. The existing database/profile/role seal is
  still mandatory.
- `@repo/auth` now constructs local auth without Google or GitHub credentials. Local
  login exists only with the sealed `local` runtime profile, `NODE_ENV=development`,
  exact bypass flag, validated loopback app origin, validated local runtime database,
  and a request from the configured origin.
- The fixed `ada@tracera.local` and `grace@tracera.local` identities create normal
  database-backed Better Auth users and sessions. Unknown identities and mismatched
  origins return 404. The landing page shows these actions locally and does not render
  unavailable OAuth actions.
- Local HTTP uses a non-secure `tracera.session_token` cookie deliberately. Deployed
  auth retains the production origin, forced secure cookies, Google/GitHub provider
  behavior, account linking rules, token encryption, and pre-storage token discarding.
- `vp run test:auth-browser` starts the app on the generated port and runs one Chromium
  test with only runtime configuration in the web/test child. Its wrapper uses the
  separately loaded generated migrator profile only for exact synthetic-fixture cleanup;
  it accepts no target arguments.
- Playwright 1.63.0 was added through Vite+ as the current stable `@latest` resolution.
  Browser reports and traces are ignored.

No migration, Core v2 stage, provider/retrieval fixture, production configuration,
OAuth application, production database, deployment, or paid call was added or used.

## Real PostgreSQL and browser evidence

The browser test used Better Auth's production database adapter and the local
`tracera_runtime` TCP connection, not a mocked session or fixture adapter. It exercised:

- discovery of the two local identities while Google/GitHub actions were absent;
- Ada login, a real session row, the normal session cookie, `/api/tracera/auth/me`, and
  preservation across a browser reload;
- a deterministic private trace inserted with runtime privileges for Ada;
- a separate Grace browser context receiving its own user/session and receiving 404 for
  Ada's trace ID plus an empty scoped search for Ada's unique trace marker;
- Ada logout followed by a 401 session lookup;
- migrator-only cleanup of the exact synthetic identities and reserved trace prefix.

The private trace and identities were synthetic. This is authentication, persistence,
cookie, and tenant-isolation evidence against real local PostgreSQL; it is not provider,
retrieval, factual-accuracy, OAuth callback, production, or release evidence.

## Configuration and migration instructions

Run:

```sh
vp install
vp run env:setup
vp run db:local:start
vp run db:local:migrate
vp run dev
```

Open the exact `http://localhost:<generated-port>` reported by setup/dev and select Ada
or Grace. Do not export auth/database variables or add OAuth credentials locally. Existing
generated L01/L02 profiles are upgraded in place without secret rotation. A copied or
mismatched generated profile is refused.

For browser validation, install the browser binary once with
`vp exec --filter web -- playwright install chromium`, keep the local database running
and migrated, then run `vp run test:auth-browser`. L04 adds no migration and ran no
production migration.
