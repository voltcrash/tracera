## Changed behavior

- Generated local/test runtime and analysis profiles now set sealed
  `TRACERA_ANALYSIS_MODE=fixture`. Those profiles require fixture mode and continue to
  reject provider credentials/endpoints. Deployed profiles reject both fixture mode and
  `AI_PROVIDER=fixture`.
- `OfflineFixtureAiProvider` provides deterministic structured generation, image text
  extraction, and normalized 1024-dimensional embeddings. Live provider construction
  still requires its API key and retains the existing adapters.
- Fixture acquisition is selected before live acquisition. It covers supported text,
  link, and image inputs; conflicting evidence; an intentionally inaccessible link; an
  unknown-fixture error; and an intentional provider failure. Missing fixtures return
  `fixture_unavailable` and never fall through to a live transport.
- The audited live transports remain unchanged and unreachable in fixture mode: hosted
  AI adapters, direct public-document fetch, Jina, Google/Bing News, GDELT, Google Fact
  Check, NewsAPI, publisher enrichment, and Internet Archive. `safeFetch` and production
  SSRF protections were not relaxed.
- The application still runs fixture calls inside its real authenticated admission,
  database persistence, tenant isolation, rate/concurrency, daily-quota, idempotency,
  and provider-spend controls.
- Successful fixture reports persist `analysisMode: "fixture"`, return it from the API,
  and show a synthetic-fixture badge on fresh and saved reports.
- `vp run test:offline-analysis` starts the local app and runs one Chromium integration
  test. Its migrator-only wrapper accepts no target and removes only fixture-marked
  checks, the two fixed synthetic identities, and `fixture` provider-spend records.

Relevant files include `packages/ai/src/offline-fixtures.ts`,

## Real database and fixture distinctions

The offline browser test used real Better Auth sessions and the least-privileged local
runtime PostgreSQL connection. It completed and persisted four analyses (text, link,
image, and conflicting evidence), replayed one result through the real idempotency
table, observed a `fixture` provider-spend row, loaded the saved synthetic badge, and
proved Grace received 404 for Ada's private report. It also exercised inaccessible and
unknown fixtures as HTTP 422 `fixture_unavailable` results and provider failure as an
HTTP 503 `analysis_unavailable` result.

The deterministic unit test replaced global `fetch` with a throwing implementation and
observed zero calls while fixture generation, retrieval, scoring, and embedding ran.
This is code-path evidence, not an operating-system network sandbox. The browser suite's
fixture branch contains no live transport; it did not make an external retrieval or AI
call.

All claims, evidence, timestamps, URLs, images, verdicts, and embeddings used by L05 are
synthetic. They do not validate factual accuracy, provider quality, retrieval recall,
latency, calibration, or release readiness. The existing Core fixture evaluator also
remains code-smoke evidence only.

## Configuration, migration, and raw blobs

Run `vp run env:setup` once to add `TRACERA_ANALYSIS_MODE=fixture` without rotating
existing generated secrets, then start and migrate the local database before `vp run
dev`. Do not add provider keys or endpoints to local/test files or the shell. Unknown
inputs are intentionally unavailable; use the documented fixtures in
`docs/environment.md`.

No schema migration was created and no production migration ran. The v1 image flow
continues to store its submitted data URI in PostgreSQL and does not invoke the Core v2
`RawBlobStore`; a local filesystem raw-blob implementation is therefore not required by
current flows. Core Task 04 must implement that boundary when it produces stored raw
bytes. L05 did not resume or pre-implement that Core stage.

## Remaining limitations and successor instructions

- L05 does not provide arbitrary offline fact checking. Only registered synthetic
  scenarios run; this fail-closed boundary is deliberate.
- Network denial is structurally tested with a throwing `fetch`, not enforced at the OS
  level. L06 owns the post-acquisition offline CI network policy.
- Real OAuth callbacks, live-provider evaluation, human-gold annotation, calibration,
  provider latency, release approval, production migration, and deployment remain
  separate and unsatisfied.
- After explicit approval, branch `local-dev/l06-workflow-ci` from this completed tip and
  target this branch while PR #8 is open. L06 should put the verified workflow in CI,
  enforce offline network policy after dependencies/images are acquired, test from a
  second clean worktree, and produce the final stack/readiness report. Do not resume
  Core implementation.
